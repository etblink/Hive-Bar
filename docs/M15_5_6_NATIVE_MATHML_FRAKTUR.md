Representative affected source forms include:

```text
Let (\\mathfrak{E}) denote the admissible extension class.
Extension invariance: (w) is unchanged under all admissible extensions in (\\mathfrak{E}).

```

## Root cause

M15.5.5 canonicalizes the owner-observed double escape convention correctly, but its compatibility layer then converts `\mathfrak{E}` into the supplementary-plane Unicode character `𝔈` before the local MathML parser runs.

JavaScript indexes strings by UTF-16 code unit. The existing parser advances ordinary non-command input one code unit at a time. `𝔈` therefore becomes two isolated surrogate halves in visible MathML content. When the response is encoded as UTF-8 those isolated halves become two U+FFFD replacement characters, matching the owner-observed `��` rendering.

The previous M15.5.5 regression could miss this because a valid contiguous `𝔈` could still occur in non-visible MathML metadata while visible content was malformed.

## Correction

M15.5.6 removes the pre-parser conversion of `\mathfrak{...}` into mathematical-alphanumeric Unicode characters.

Instead, the local MathML parser recognizes `mathfrak` as a native style command and emits structural MathML:

```html
<mstyle mathvariant="fraktur"><mrow><mi>E</mi></mrow></mstyle>
```

This keeps TeX styling as MathML styling and prevents supplementary-plane surrogate splitting.

The existing M15.5.5 double-escape canonicalization remains unchanged, so owner-observed `\\mathfrak{E}` is first canonicalized to `\mathfrak{E}` and then rendered natively.

## Regression requirements

The candidate must pass the full deterministic quality gate on Ubuntu and Windows plus regressions proving that:

1. direct `\mathfrak{E}` renders as `mstyle mathvariant="fraktur"` with ordinary `E` content;
2. the owner-observed double-escaped Hive forms render the same native Fraktur MathML;
3. neighboring symbols such as `\in` continue to render correctly;
4. `mathcal` and `mathbb` native MathML style behavior remains unchanged;
5. rendered output contains no literal precomposed `𝔈` generated by the compatibility layer;
6. rendered output contains no U+FFFD replacement character; and
7. rendered output is byte-stable under UTF-8 encode/decode round-trip.
